The console is one page and a list. It can create, suspend, reactivate and delete a workspace. You cannot click into one. There is no way to change a customer's plan anywhere in the product, so an operator who upgrades and pays stays capped on Starter forever.

Two of the three endpoints added today — restore and purge — have no UI at all, and the delete dialog still tells you deletion is permanent. It stopped being permanent this morning.

What exists today

Access is gated on staff_users.is_platform_admin, re-read from the database on every request, answering 404 rather than 403 so the console does not advertise itself. That part is well built and is not being touched.

Build now

Ordered by how often you would reach for it, multiplied by how much it hurts when it is missing. Items 1 and 2 are the ones you would hit on your first support ticket.

01 Open a workspace and see everything about it api + ui

Today the console is a list you cannot click. A support email arrives and there is nowhere to look. This is the page every other button lives on, so it comes first. It shows the three live URLs, plan and usage against caps, onboarding progress, configuration health as booleans (never secrets), the staff roster with last-login and lockout state, recent operational shape, and the danger zone.

GET /api/v1/platform/tenants/{id} — does not exist today Detail page + "why can't they take a booking" answered at a glance
02 Make deletion tell the truth, and make restore reachable my bug verified

I made deletion recoverable this morning and did not update the interface. The dialog still says "It cannot be undone", which is now false, and the list filters deleted workspaces out — so the restore and purge endpoints I built are unreachable from the product. A customer who deletes by mistake on Monday cannot be helped on Tuesday. This is a correctness fix, not a feature.

03 Change a customer's plan commercial verified

Nothing in the entire product can move a workspace between plans. Creation hardcodes Starter, and the tenant's own update schema deliberately excludes the field — with a comment saying plan changes belong to the platform console. The console has no such endpoint. You cannot take money for an upgrade.

platform/router.py:282 subscription_tier hardcoded 'STARTER' tenants/schemas.py:96 "Plan changes belong to the platform console" platform console …has no plan endpoint
04 Record who did it audit verified

Database triggers write an audit trail for seven tables, capturing an actor id from a session variable. The only function that sets that variable has zero callers — it is dead code. So every audit row ever written records what changed and never who changed it. An afternoon's work, and it is a hard prerequisite for support access: an impersonated write would otherwise be indistinguishable from the customer's own.

core/database.py:181 def get_db(...) sets actor/role/ip/request GUCs grep -rn get_db → the definition, and nothing else
05 Show notification delivery support

"Our customer never got the confirmation email" is the highest-volume ticket in this category and there is no screen for it anywhere in the product. The table already exists with status, channel, recipient and gateway message id. This is a read of data you are already collecting.

06 Require MFA on platform-admin accounts security

These accounts can suspend and purge every customer's data. MFA is per-user opt-in today, so that power currently sits behind one password. Cheap, and it should land before support access rather than after.

Build next

Worth doing, in this order, once the six above are in.

07 Support access — consent-gated, read-only, time-boxed the big one

"Log in as this customer" is the most-requested console feature anywhere, and the mechanism here is already 90 % present — which is exactly the danger. Roughly twenty lines would do it badly. The guardrails are not optional: the tenant grants a window and can revoke it, sessions are read-only by default and never refreshable, tokens are minted for a synthetic support principal rather than impersonating a named employee, a banner shows the customer while it is live, and every session is logged. Blocked on item 4 — without an actor, support writes are unattributable.

08 Meter the billable dimension commercial

Seat limits are enforced; vehicles and locations are not — and vehicles are what the plan intends to charge on. There is a usage function that computes all three and is consumed by nothing.

09 Cross-tenant lookup support

A renter emails your support address. You have no way to tell which of forty workspaces they belong to. Email, slug, or confirmation number in — workspace out. One query; saves ten minutes per misrouted ticket.

10 Platform action log, and export on behalf compliance

Suspend, delete and purge currently exist only as log lines. And a departing customer whose administrator has already left has no way to get their data out — the export exists but is scoped to the caller's own workspace.

Deliberately not building

At five to fifty tenants these cost more than they return. Recorded so the decision is visible rather than an oversight.

Fine-grained platform roles and approval workflows

One boolean is the right design for a team that fits in a room. Revisit when there are people who should see billing but not customer data.

MRR charts, cohort retention, funnel dashboards

Stripe plus a SQL client covers this. Building it here means maintaining a second, wronger copy of Stripe's numbers.

Per-tenant feature flags · SSO for admins · in-console messaging · SLA tracking

No flag infrastructure exists, MFA on a flag is enough at this headcount, email and a helpdesk already work, and nobody has signed an SLA.

A separate console on its own hostname

The unlinked route inside the admin app is right for now. Worth recording the trade-off: the console is served from a tenant hostname, so any cross-site scripting in the tenant app reaches it. The slug is already reserved, so the move stays available without a migration.

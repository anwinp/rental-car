Making the sold features real

Four capabilities are on the price list and are not deliverable. This is what each one actually needs, what it costs, and the order I would take them in — starting with the ten-minute change that stops the misrepresentation today.

Before anything is built. Untick corporate_accounts, telematics and api_access on every plan at rcm-admin.ceez.ai/platform/plans. That takes a minute and is the only item here with a deadline: every hour those boxes stay ticked, the pricing page promises things the product cannot do. Leave advanced_reporting ticked — it is partially real and finishing it is the first build below.

01Advanced reporting — finish it

Size ~2 days Blocked on nothing Closest to done

Two endpoints trigger Celery tasks and return 202. The tasks compute a result dict and return it to nowhere: there is no report table, no retrieval endpoint, and the admin page is hidden behind VITE_SHOW_UNBUILT. A tenant can start a report and can never see one.

Build

  1. generated_reports — tenant, kind, parameters, status, row counts, the object key of the file, requested_by, timestamps. Tenant-scoped with RLS like everything else.
  2. Write the output to object storage. MinIO is already deployed and the export feature already writes zips through it, so this is reuse, not new infrastructure.
  3. GET /reporting/reports and a short-lived download URL. The report is the deliverable; a 202 is not.
  4. Unhide the page and give it a list, a state per row, and a download. The nav entry already exists behind the flag.
  5. Two more reports beyond revenue and utilisation, chosen from what operators actually ask for — my guess is fleet ageing and a tax summary, but that is a guess.

Worth doing first regardless of priority: it is the only one of the four where most of the computation already exists, so it converts a hollow promise into a real feature faster than anything else here.

02API access — build the machine door

Size ~3 days Blocked on a scope decision

There is no machine authentication anywhere in the system. Every route authenticates a human through a session cookie. The API_PARTNER role exists in the database enum and grants nothing.

Build

  1. api_keys — tenant, label, hash of the key, prefix for display, scopes, created_by, last_used_at, expires_at, revoked_at. Store a hash, never the key: the same rule the Stripe credentials follow, for the same reason.
  2. Issue once, show once. The full key is returned by the create call and never again, with the UI saying so before the button is pressed.
  3. An X-API-Key dependency that resolves the tenant from the key itself. It must bind app.current_tenant_id exactly as a session does, so RLS covers machine callers with no second implementation to keep in step.
  4. Scopes, enforced. At minimum read and write, per domain. A key that can do everything is the one that leaks.
  5. Its own rate limit, keyed on the key, plus last_used_at so a customer can spot a key that is still live and should not be.
  6. Public documentation for the subset that is supported. An API nobody can read the shape of is not a feature.
Decision needed

How wide is the API? My recommendation: read-only to start — availability, fleet, reservations, customers — plus creating a reservation. That covers the integrations people actually ask for and keeps the blast radius of a leaked key small. Full write access across every domain is a much larger surface to secure and to support.

03Corporate accounts — greenfield

Size ~8 days Blocked on what it must do

A twelve-line router with a health check, and no tables. Everything the name implies has to be built. It is also the most valuable of the four commercially: negotiated corporate rates are how a rental operator wins contracted business rather than walk-ups.

Build

  1. corporate_accounts — the company, billing address, payment terms, credit limit, an account code the counter can search.
  2. corporate_rate_agreements — negotiated rates per vehicle class, valid between dates. This must join the existing rate-selection path rather than sit beside it, or a corporate booking will quietly be quoted the public price.
  3. corporate_bookers — who may book on the account, and the CORPORATE_BOOKER role already in the enum, finally meaning something.
  4. Bill to account, not to card. A reservation gains an optional account reference; the counter can close a rental without taking payment, and the account is invoiced.
  5. Statements — what a company owes across all its bookings in a period. This is the thing a finance department asks for on day one.
  6. Admin UI, plus a booker-facing view, plus the account picker at the counter.
Decision needed

What is the minimum that counts as shipped? The honest small version is accounts + negotiated rates + bill-to-account, leaving statements and self-service booker portals for later. That is roughly half the estimate. Tell me if invoicing has to be in the first cut, because it changes the shape considerably.

04Telematics — needs a provider before it needs code

Size ~5 days once decided Blocked on hardware and provider

The table is already there and well designed — partitioned by month, with vehicle, device, position, speed, heading and odometer. Nothing writes to it and nothing reads it. Notably, the schema is the easy part; the integration is the work, and it cannot start until it is known what is sending the data.

Build, once a provider is chosen

  1. An ingest endpoint per provider, authenticated by a shared secret and signature — the webhook pattern the Stripe receiver already establishes. Devices cannot hold a session, so the signature is the authentication, and the same three checks apply: signature over raw bytes, a timestamp tolerance, constant-time comparison.
  2. Device registration mapping a device id to a vehicle, so a reading can be attributed at all.
  3. Odometer reconciliation. This is the payoff and the trap: telematics odometer and the counter's typed odometer will disagree, and deciding which wins — and what happens to a mileage charge when they do — is a business rule, not a technical one.
  4. Live map and last-known position in the back office; an alert when a vehicle leaves an agreed area or an overdue rental stops moving.
  5. Retention. Position history is personal data about a driver. The partitions exist; a drop policy does not.
Decision needed

Which devices? A managed provider (Geotab, Samsara) means an integration against a documented API and no hardware to support. Generic OBD dongles posting JSON are cheaper per vehicle and put the support burden on you. Until this is answered there is nothing to build against, which is why this one sits last regardless of its appeal.

05Stop this recurring

Size ~half a dayBlocked on nothing

The gating mechanism worked perfectly while gating three things that do not exist, which is why nobody noticed. That is the same failure mode as every other bug found this week, and it has the same kind of answer.

tests/plan_enforcement_lint.py already asserts that every column of plans is read by a query somewhere. Extend it to features:

  • Every key in the FEATURES registry must appear in at least one require_feature(...) call or an explicit allowlist entry with a reason.
  • Every gated router must have at least one route beyond /health — the check that would have caught corporate_accounts, whose router is gated, mounted, and empty.
  • Fail the build otherwise.

Half a day, and it is the only item here that prevents a repeat rather than fixing an instance.

An alternative worth considering

Four features is roughly three and a half weeks. If the aim is a coherent product rather than a full checklist, drop telematics and corporate accounts from the price list entirely and sell Growth on capacity plus channels and reporting. Both can return when they are real. A short list of things that all work sells better than a long one where three entries lead to a support conversation, and it is a considerably cheaper path to a defensible Enterprise tier.

Making plans enforceable

Three of a plan's attributes now bite. Four do nothing at all, and one of those is a button in the console that writes a date no code ever reads. This is what it takes to close the gap, in the order the pieces depend on each other.

01Where it stands today

Verified against production by exercising each path, not by reading the code.

AttributeStatusWhat actually happens
max_staff enforced 402 at invite, invite acceptance, reactivation, and both console paths. Pending invitations hold seats.
max_vehicles enforced 402 on single create and on bulk import, checked for the whole batch before validation.
max_locations enforced 402 on create.
is_active enforced An archived plan cannot be newly assigned. Workspaces already on one keep it.
is_default enforced Signup reads the flag instead of a hardcoded literal.
trial_ends_at read by nothing A trial never ends. The console's "Extend trial 14 days" writes a date zero lines of code consult.
subscription_ends_at read by nothing Same. A lapsed subscription changes nothing.
price_cents, currency, billing_period data only Nothing charges a tenant. The Stripe integration is per-tenant, for their renters' cards.
— features — no such concept Plans cap counts and nothing else. OTA channels, telematics, the agent tooling and reporting are on for every tenant on every plan.

The load-bearing observation

Every gap below is the same gap: a column exists, a UI writes to it, and no read path consults it. That is also how GROWTH came to be unassignable while PROFESSIONAL was silently unlimited, and how max_vehicles sat in the admin UI for months while a Starter workspace could hold ten thousand cars.

So Phase 5 matters more than its position suggests. Everything before it fixes today's holes; Phase 5 is what stops the next one being found by a customer.

02Phase 1 — Make time mean something

Size ~1 day Blocks Phase 4 Needs a decision yes

trial_ends_at and subscription_ends_at are the two most damaging gaps, because the console presents them as working controls. An operator extends a trial, sees a success message, and has changed nothing.

What to build

  1. One function that answers "may this workspace trade?" There is already assert_tenant_trading() gating the storefront on tenant status. Extend it — rather than adding a parallel check — to also fail when a workspace is on a trial or subscription whose date has passed. One function, so the rule cannot be enforced in three places and disagree.
  2. A daily sweep that moves state, not just blocks reads. app/worker/tasks/tenant_maintenance.py already runs tenants.sweep_unverified on RedBeat at 03:30 UTC. Add tenants.sweep_expired beside it: flip lapsed workspaces to a terminal status so the state is visible in the console rather than computed invisibly at every request.
  3. Warn before the wall. Email at 7 days, 3 days, and on the day. A trial that dies silently at 03:30 with no warning is a support ticket and a refund conversation, not a conversion.
  4. Show the clock. The tenant's own admin should display days remaining. Today only the platform console knows.
Decision needed before I build this

When a trial or subscription lapses, what stops? My recommendation: the storefront stops selling, staff keep signing in. That mirrors how suspension already behaves and it is the deliberate split in the existing code — an operator locked out of their own back office cannot export their data or reach a payment page, so a hard lockout converts worse and is harder to reverse. The alternative is a full lockout, which is simpler and more coercive. Tell me which.

03Phase 2 — Plans that gate features, not only counts

Size ~2 days Blocks nothing Needs a decision yes

A plan can currently say how much but never what. Every tenant on every plan gets OTA channel integration, telematics, the AI agent tooling, corporate accounts and the full reporting suite. If Growth is meant to unlock capability rather than bigger numbers, this is the missing half of the pricing model.

What to build

  1. plan_features(plan_code, feature_key, enabled) — a join table, not a JSON blob on plans. A blob cannot be queried for "which plans include telematics", which is the first question anyone asks when repricing.
  2. A registry of feature keys in code, not free text. The database stores which plan has what; the application owns the vocabulary. A typo'd key that silently grants nothing is exactly the failure mode this whole document is about.
  3. One dependency, require_feature("ota"), applied at the router level so a whole surface is gated in one line and the gate is visible in the route table during review.
  4. Hide what is not included. Tenant config already ships to the browser at boot; add the resolved feature set so the admin nav does not advertise a page that 402s.
  5. Checkboxes on the plans page, so this is administered where caps already are.
Decision needed

Which capabilities are premium? The plausible candidates are OTA channels, telematics, the agent assistant, corporate accounts, advanced reporting and API access. I would not guess at this — it is a pricing decision, not an engineering one. Give me the split and I will build to it; give me nothing and I will build the mechanism with every feature enabled everywhere, which is at least honest.

04Phase 3 — Let tenants see where they stand

Size ~half a day Blocks nothing Needs a decision no

Enforcement a customer cannot see is indistinguishable from a bug. Today a Starter workspace discovers its 25-vehicle cap by being refused mid-task, with no prior signal and no page showing the number.

get_usage() already computes everything needed and is surfaced nowhere except a seat count buried in the team page. This phase is mostly wiring:

  • A plan-and-usage panel in the tenant's own settings: what they are on, what they have used of each cap, when their term ends.
  • A warning at 80 % of any cap, so the refusal is never the first news.
  • The 402 already names the plan and the cap. It should also link to the upgrade page, once one exists.

05Phase 4 — Charging for the plan

Size ~1 week Blocks nothing, but pointless before Phase 1 Needs a decision yes

This is the one genuinely large piece, and the one most easily got wrong by starting early. price_cents is a note to yourself until a provider is chosen.

Worth being explicit about a distinction that has already caused confusion: the Stripe code in this repository is per tenant — each rental company's own gateway, charging their renters. Platform billing is a second, separate integration, with its own account, its own webhooks and its own reconciliation.

Sequence

  1. Provider and account. Stripe Billing is the obvious default given Stripe is already a dependency, though the existing usage shares nothing but the vendor name.
  2. tenant_subscriptions — external subscription id, status, current period end, cancel-at-period-end.
  3. Webhook receiver. The processed_webhooks table and its idempotency pattern already exist and should be reused rather than reinvented.
  4. Webhook drives subscription_ends_at, which Phase 1 already enforces. This is why Phase 1 comes first: build it now and the enforcement is already waiting.
  5. A self-serve upgrade path from the tenant admin, and dunning on failed payment.
Decision needed

Provider, and whether upgrades are self-serve or sales-assisted. Everything else follows from those two answers.

06Phase 5 — Stop finding these by hand

Size ~half a day Blocks nothing Needs a decision no

Three bypasses turned up in this week's audit: bulk import ignored max_vehicles entirely, and two console paths ignored max_staff. All three were found by reading every write path by hand. That does not scale and will not be repeated reliably.

This repository already has the right shape of answer in tests/tenant_sql_lint.py, which walks the AST looking for queries that touch tenant tables without a tenant predicate, with a small allowlist where crossing is legitimate. The same technique applies here:

  • Enumerate every function that inserts into a capped table.
  • Assert each one reaches assert_within_limit, or appears on an allowlist with a written reason — the first staff member of a brand-new workspace, for instance, which cannot exceed any valid cap.
  • Fail the build otherwise.

A second, blunter check is worth having beside it: assert that every column on plans is read somewhere outside the plans router itself. That single test would have caught trial_ends_at, max_vehicles and max_locations on the day each was added, instead of months later.

07Order, and what I need from you

Phases 1, 3 and 5 need nothing from you beyond the trial-expiry policy and can start immediately. Phase 2 needs the premium split. Phase 4 needs a provider.

PhaseSizeBlocked on
1 · Time~1 dayLockout policy — storefront only, or everything
5 · Lint~0.5 dayNothing
3 · Visibility~0.5 dayNothing
2 · Features~2 daysWhich capabilities are premium
4 · Billing~1 weekProvider; self-serve or sales-assisted

I would take them in that order: 1, 5, 3, 2, 4. Phase 5 sits second on purpose. It is half a day, it is the only item that prevents recurrence rather than fixing an instance, and every phase after it lands safer for having it.

One thing deliberately not proposed

Retroactive enforcement. A workspace that exceeds a cap after a downgrade keeps everything it has and simply cannot add more. Disabling vehicles somebody is mid-rental with, or locking staff out of a shift in progress, would be worse than the overage and would land on the renter at the counter rather than on the customer who downgraded. If you want a different policy here, say so — but it should be a deliberate choice, not a default.
